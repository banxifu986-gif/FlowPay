# 规格：007 多轮澄清覆盖与文档召回

状态：草案（2026-11-17 已与 Ban 逐项确认需求与验收口径；待 clarify → plan → tasks 后由 Pi 实施）
前置：006 已提交于 `feature/006-launch-hardening`（未 push）；96 题双跑报告与归因脚本已提交。
基线：2026-11-17 C 臂（治理开、混合检索）96 题结果——总通过 23/96、证据全中 32/96、多轮 14/64、单轮 9/32。

## 背景

96 题双跑（每类前 16 题，A 基线 18/96、C 生产默认 23/96）暴露的问题不是“对话卡住”，而是澄清质量与召回：

- 64 道多轮题里 58 道追问过，但**没有一道问全题库要求的 5–6 类信息**：goal 从未被问，symptom_details 39 题、occurrence_time 36 题、api_version 21 题漏问。现有 `ask_user` 只能报查询条件字段（账户/环境/各类编号），目标、现象、时间、版本这些背景主题没有入口。
- 多轮失败 50 题中 34 题证据未全：文档命中 55%、记录命中 53%；通过题的对应命中是 71% 和 80%。证据漏是主因，不是追问结束。
- 真正停在追问上的只有 8 题（A 7、C 8），其中 3 题证据已齐——等待轮原样回传 worker 问题、丢弃调查报告，用户看不到“已经查到了什么”。另有单轮题 A 20 / C 22 个 waiting_user 轮因基准脚本提前结束从未进入 signals，报表低估了澄清频率。
- 单轮检索题文档命中仅 23/48（48%）；两个文档型题型（simple_retrieval 7/16、multi_document 2/16）合计 32 题只过 9 题。检索是独立于澄清的第二瓶颈。
- 登录态已由服务端绑定 `account_id`（specs/005 的 scope_overrides），但工具 schema 仍把 `account_id` 标为必填，模型仍可能向商户索要本可自动确定的信息。

## 目标

1. 澄清覆盖：多轮排查先查能查的，再一次性问全尚缺的条件与背景主题；等待轮先给结论再提问。
2. 澄清状态跨轮可追踪：已问、已回答、明确拿不到，不重复索要。
3. 登录态账户不被重复索要。
4. 文档召回：先建立离线检索评测定位瓶颈，再落一个召回改造。
5. 评测口径修复：基准报表与归因不再漏计最终轮澄清信号。

## 用户故事

### US1（P0）先查后问，一次问全

用户报告排查问题但信息不全时，系统先用已有条件执行可以执行的查询（文档调查不依赖账户，先跑），只有当证据不足或业务查询确实缺必需条件时，才向用户发问；一次追问覆盖所有尚缺的条件与背景主题。

- **Given** 用户描述了现象但没有账户与编号，**When** 系统处理，**Then** 文档调查先执行，业务调查标记为缺条件；本轮回答先列出已查到的结论，再一次性索要账户、环境、编号与缺失的背景主题，状态为等待用户。
- **Given** 用户已提供账户与环境，但缺少发生时间，**When** 证据不足以定位记录，**Then** 系统先执行可用查询，再在追问中索要时间与编号，不重复索要已提供的账户与环境。
- **Given** 已有报告足以回答用户问题，**When** 系统收束本轮，**Then** 直接作答，不发起新的追问。

### US2（P0）等待轮带结论

系统需要追问时，用户看到的是“目前已查到什么 + 还需要什么”，而不是一条空泛的问题。

- **Given** 文档调查已返回相关规则片段，业务调查缺账户，**When** 本轮以追问结束，**Then** 回答包含已查到的规则结论与引用，再列出仍缺的账户/编号。
- **Given** 本轮没有任何查询产出，**When** 系统追问，**Then** 明确说明尚未查到结论，并列出所需信息。

### US3（P1）澄清状态跨轮不重复

系统记住每个主题是已问过、已回答，还是用户明确拿不到；后续轮次不再重复索要同一主题。

- **Given** 上一轮已问过发生时间且用户已回答，**When** 下一轮继续排查，**Then** 不再索要发生时间，直接使用该值。
- **Given** 用户对“账户编号”回复“查不到/不知道”，**When** 后续轮次仍缺该信息，**Then** 不再追问该主题，照常给出结论并明确标注哪些未能确认。
- **Given** 同一轮两个调查员都需要用户补充信息，**When** 本轮收束，**Then** 只产生一条合并后的追问，不出现两条独立追问。

### US4（P1）登录态账户不再索要

已登录商户的账户由系统绑定，助手不再向用户索要；内部账号与无绑定的会话行为不变。

- **Given** 商户会话已绑定账户，**When** 用户发起排查，**Then** 业务查询直接使用绑定账户，追问中不出现账户编号。
- **Given** 内部账号或未绑定会话，**When** 缺少账户，**Then** 仍按现有规则向用户索要。

### US5（P1）文档召回诊断与改进

先量化“必需文档能不能被召回到”，再依据诊断结果落一个召回改造。

- **Given** 题库的必需文档集合，**When** 跑离线检索评测，**Then** 输出两种查询口径（只用首条消息、首条消息+完整披露事实）下 top-k 的必需文档 recall，以及纯向量与混合检索的差异。
- **Given** 诊断报告定位到瓶颈，**When** 实施一个召回改造，**Then** recall@10 相对基线提升 ≥10 个百分点，且单轮检索题任务通过与证据命中不下降。

### US6（P2）评测口径修复

基准报表与归因脚本把最终轮澄清信号计入统计，验收指标可被准确测量。

- **Given** 一道题在最后一轮以追问结束，**When** 生成报表与归因，**Then** 该轮 waiting_user 被计入信号与失败原因，不再被漏掉。

## 边界情况

- **用户改口账户或环境**：查询条件按现有改口语义作废旧条件与旧查询；已收集的背景主题（目标/现象/时间/版本）保留，除非用户同时改口该主题。
- **先说拿不到、后又提供**：该主题从“不可提供”改为“已回答”，后续轮次恢复使用，不再视为缺失。
- **同一主题出现多个值**：以最新一次为准，并在简报中注明旧值已被替换。
- **轮次预算耗尽**：不再发起新的追问，按已有证据作答，并明确标注未能确认的部分。
- **必需文档不在知识集合**：检索诊断记为不可召回，单独统计，不归因于查询改写或排序。
- **等待轮没有任何查询产出**：仍给出追问，但明确说明“目前尚未查到结论”，不伪造摘要。

## 范围外

- 全量 300 题验收；本轮固定 96 题样本。
- 混合检索默认开关的最终去留（由 US5 诊断与后续全量评测决定）。
- 重排序模型、分块策略大改、多路查询改写等重检索改造（除非 US5 诊断直接指向）。
- 前端交互改版；等待轮仍以文本消息呈现。
- manual-loop 阶段的行为变更：共享工具 schema 可扩展，但该阶段提示词与编排不改。
- 跨会话记忆、用量守卫、鉴权边界的既有语义。

## 需求

### 功能需求

- **FR-1**：追问分为两组字段——`conditions`（账户、环境、支付/请求/事件/投递/端点/客户编号）与 `topics`（goal 目标、symptom_details 现象、occurrence_time 时间、api_version 版本）；一次追问可同时包含多个条件与主题。
- **FR-2**：同一轮内多个调查员的缺项合并为一条追问；本轮只允许一个待回复追问。
- **FR-3**：先查后问——不阻塞查询的主题不得导致提前发问；能执行的查询先执行，只有在证据不足或业务查询缺必需条件时才追问。是否足够由 synthesize 的同一次模型调用做结构化决策：返回“直接作答”或“追问”，追问分支携带已查结论摘要与仍缺条件/主题。
- **FR-4**：等待轮的回答必须包含“已查到的结论摘要 + 仍缺信息的追问”；没有查询产出时明确说明。不得原样转发调查员给内部看的问题文本。
- **FR-5**：澄清状态跨轮持久化，至少记录：已问主题、已回答主题与值、用户明确拿不到的主题；后续轮次注入简报，已问/已回答/不可提供的主题不再重复索要。状态更新复用 plan 节点每轮已有的模型调用：plan 在拆解任务的同时输出本轮用户消息中的主题回答、不可提供声明与主题值，不新增抽取调用。
- **FR-6**：用户明确表示“查不到/不知道”时，该主题记为不可提供，不再追问；证据不足时照常作答，并在结论中标注未能确认的部分。
- **FR-7**：商户会话中被服务端绑定的隔离列（账户）不再要求模型填写或向用户索要；内部会话与未绑定会话的必填行为保持不变。
- **FR-8**：离线检索评测按题库必需文档集合计算 recall@k；查询口径三种——“首条消息”（initial）、“首条消息+今天的实际用户回复”（observed，代表改写能拿到的信息）、“首条消息+全部可披露事实”（full，仅作上界）；对比纯向量与混合检索，报告 top-k 与口径差异；不调用聊天模型。
- **FR-9**：依据诊断选择并实施一个召回改造；若诊断显示查询缺信息是主因，改造可以是把澄清得到的事实拼入查询；若显示召回本身不足，改造可在混合检索、分块或查询改写中选一项。实施后在相同 96 题上与基线对比。
- **FR-10**：基准报表与归因脚本把所有以 waiting_user 结束的轮次计入信号、偏离与失败原因统计——包括多轮题的最终轮与单轮题的等待轮；单轮题不能再因提前结束而漏记。
- **FR-11**：验收运行固定模型 `deepseek-v4-1-flash-economy-261017`、固定 96 题样本、固定与 C 臂相同的治理与检索配置；基线复用 2026-11-17 C 臂结果。
- **FR-12**：synthesize 的作答/追问决策写入事件，至少含 `mode`（answer/clarify）、来源（model/fallback）、仍缺主题与条件；覆盖率统计读取该事件、`ask_user` 事件与检查点里的已回答主题三处，不依赖单一通道。

### 关键实体

- **澄清状态（ClarificationState）**：已问主题、已回答主题与值（主题 → 值）、不可提供主题；随会话检查点持久化，与查询条件（Case）分离。更新来源是 plan 节点的既有模型调用，不新增抽取请求。
- **澄清请求（ClarificationRequest）**：缺失的条件 + 缺失的背景主题 + 面向用户的合并问题文本。
- **检索诊断报告（RetrievalDiagnosis）**：两种查询口径下 top-k recall、纯向量与混合检索差异、瓶颈结论与建议改造。
- **基准结果行（BenchmarkRow）**：既有逐题结果；澄清信号需包含最终轮。

## 成功标准

### 可度量结果

- **SC-1**：在确实发起追问的多轮题上，整题合并后的“已问主题/条件 + 已回答主题（含从首条消息抽取）”覆盖题库必需类别的比例 ≥90%；用户已提供的信息不要求再问。
- **SC-2**：所有以 waiting_user 结束的轮次，回答 100% 包含已查结论摘要（无结论时明确说明）。判定以确定性假模型的集成测试为准（覆盖“有结论”与“无结论”两态）；96 题基准侧做辅助抽检并记录抽检结果。
- **SC-3**：同一主题在同一会话中被重复追问的次数为 0；已回答或不可提供的主题不再被索要。
- **SC-4**：同模型、同 96 题下，总通过 ≥23、多轮通过 ≥17、证据全中 ≥32、单轮通过 ≥9（不下降）。
- **SC-5**：离线必需文档 recall@10 相对 initial 基线提升 ≥10 个百分点。`observed` 上界用于批量前诊断；最终以新臂 actual 口径（initial + 检查点 `clarification.answers` 实际收集到的主题值）确认；`full` 只作上界、不算验收。端到端单轮检索题任务通过与证据命中不下降。
- **SC-6**：基准报表与归因中，所有 waiting_user 轮次的计入率为 100%（A/C 两臂各 101 轮：多轮 A 81 / C 79，单轮 A 20 / C 22；其中多轮最终轮 A 7 / C 8）。
- **SC-7**：`make quality` 全绿；既有测试基线保持为空。

## 假设与依赖

- **模型口径**：Ban 确认 coding plan 的 `deepseek-v4-1-flash-economy-261017` 与 2026-11-17 基准所用模型在参数与上下文长度上一致，因此直接复用 C 臂 96 题结果作为基线；`.env` 已切换并同步备份键。
- **样本口径**：每类前 16 题，共 96 题；不扩到全量 300。
- **基线配置**：治理项开启、检索路径与 C 臂一致；基准脚本继续显式声明隔离项。
- **manual-loop**：共享 `ask_user` schema 的扩展保持向后兼容，该阶段的提示词与行为不变。
- **无新依赖**：检索诊断复用现有知识集合与嵌入服务；不新增第三方包。
- **无聊天模型调用**：离线检索评测只走嵌入与知识检索，不产生模型用量。
- **数据来源**：题库 `flowpay-dataset` 的 `required_documents` / `planned_evidence_ids` 与 `conversation` 元数据作为评测标签；产品运行时不读取题库元数据。

## Clarifications

### Session 2026-11-17

- Q: 用户回复追问后，系统应如何把“已回答的主题与值”记录下来供后续轮次使用？ → A: 复用 plan 节点每轮已有的模型调用，在拆解任务的同时输出澄清状态更新；不新增抽取调用。
- Q: “证据是否足够、要不要追问”由谁判断？ → A: synthesize 的同一次模型调用做结构化决策，返回“作答”或“带结论摘要的追问”。
- Q: 单轮题以 waiting_user 结束的轮次是否纳入 US6 统计？ → A: 纳入。SC-6 覆盖所有 waiting_user 轮次（A/C 各 101 轮），单轮题不能因 `play()` 提前 break 而漏记。
- Q: pending 是否继续短路整轮、让所有调查员一起收束？ → A: 不再。pending 只收束发起追问的那个调查员，其余调查员继续完成可执行的查询，本轮仍以 waiting_user 结束。这是对 specs/001 plan「waiting_user 经 pending 置位短路 worker 循环」的显式取代，用于满足 007 US1/FR-3 的“先查后问”。
- Q: 覆盖率只统计“问过的主题”，还是也统计“已回答的主题”？ → A: 已问 + 已回答（含 plan 从首条消息抽取）；用户已提供的信息不要求再问，不能算漏问。
- Q: 模型在 synthesize 层直接追问时，主题怎么进入统计？ → A: synthesize 发 `clarification.decided` 事件（mode/来源/缺项），覆盖率与报表同时读取 `ask_user` 事件、该事件与检查点已回答主题。
- Q: 什么时点算“已经问过”、后续不再问？ → A: 只有 synthesize 最终采纳且用户可见的 clarify 决策（含确定性回退）才写入 `asked_topics`；worker 提议但模型改判作答的不算问过。pending 承担同一轮内的去重。
- Q: 检索诊断的 full 口径能否直接当作改写后的验收指标？ → A: 不能。full 是包含题库全部可披露事实的上界；observed（首条消息+今天实际出现的用户回复）用于批量前诊断，最终以新臂 actual（实际收集到的主题值）确认；full 只记录为上界。
- Q: observed 口径的复测是否直接采用 full 的检索结果？ → A: 不。observed 必须用自身查询文本检索；复测发现初版 `collect` 把 observed 误用了 full，该结果作废，修复后重跑才算数。
- Q: observed +2.6pp 是否足以判定 T027 查询改写失败？ → A: 不足以。observed 来自旧 C 臂的原始回复，产品改写实际使用新系统抽取出并保存的 `clarification.answers`；旧臂没问到的类别不会出现在回复里。T027 暂保留，最终以新臂 actual 口径判定；actual <10pp 时再决定补澄清覆盖、调整改写或撤换。

既有决策（同一次 grill 会话）：

1. **范围**：双轨——US1 澄清覆盖与证据收敛 + US2 检索诊断与改进；不分拆到 008。
2. **发问机制**：worker 仍负责调 `ask_user`；同一轮多 worker 缺项合并；synthesize 负责把已有结论摘要与一次问全的追问拼成最终回答。
3. **主题集合**：两组字段对齐题库六类；`conditions` 保留现有枚举，新增 `topics`：goal / symptom_details / occurrence_time / api_version。
4. **跨轮状态**：新增独立 `ClarificationState`；`Case` 继续只存查询条件，不混入背景主题。
5. **问询时机**：先查后问；证据不完整或业务查询缺 scope 才追问；证据足够直接作答。
6. **等待轮输出**：必须附已有结论摘要再追问；不做“证据足够则强制作答”之外的额外判定。
7. **拿不到信息**：用户明确“查不到/不知道”时记为不可提供，不再追问，照常作答并标注未确认项。
8. **登录态**：已绑定的商户账户不再要求用户提供；内部会话不变。
9. **检索验收**：先诊断后改；诊断口径两种（首条消息 / 首条消息+完整披露事实），题库无参考检索词；改进后 recall@10 相对基线 +10pp，单轮不降。
10. **评测协议**：模型 `deepseek-v4-1-flash-economy-261017`，复用今日 C 臂 96 题结果作基线，后续同 96 题。
11. **验收门槛**：机制硬门（覆盖 ≥90%、等待轮 100% 带结论、重复问 0）+ 方向性提升（总 ≥23、多轮 ≥17、证据 ≥32、单轮 ≥9）；不要求统计显著。
12. **覆盖统计范围**：只统计确实发起追问的题；证据足够直接作答的题不计入漏问。
