# FAQ 套件契约（计划）

## 1. 发布、加载与隔离

- 同一独立 release 复用摄入器组名 `published_knowledge`（`agent_knowledge`）、`canonical_agent_data`（运行快照）、`faq_benchmark_dev`、`faq_benchmark_test`（后两者仅评测）。知识路径在 `data/knowledge/`；业务清单与快照放 `data/generated/canonical/`；题单和标注分文件、按 split 存放。完整清单覆盖所有组；运行视图仅携带清单和运行组，不携带题面、金标或评测记录。
- FAQ profile 由显式根路径选择，并校验本地可信的 release 摘要、期望 collection / 向量空间、业务清单摘要和只读策略。运行视图缺评测组文件是预期；加载器只验证实际使用的组，制包验收需验证全部组。缺运行组、缺所选 split 或版本不匹配分别在相应场景拒绝，不回退旧套件、旧配置或旧集合作兜底。
- 公开 FAQ 历史稿允许被检索，但只有适用版本是计分证据；固定版 collection 不能混入原 `flowpay_docs_v1_bge_m3` 或非 FAQ 资料。新的构建只写 FAQ 目标 collection；启动／运行均核对实际来源身份。
- FAQ 模式的会话、检查点、trace、记忆或反馈不得与旧模式共享。Web 只复用现有 `/api` 和 SSE，不新增生产入口。FAQ 模式只监听回环地址，为模拟身份配置独立的账号与令牌密钥；密钥由环境供应，账号文件不是发布物。

## 2. 调用入口

| 入口 | 参数与行为 |
| --- | --- |
| `python -m scripts.faq freeze` | `--source <authoring-root> --output <new-release-root> --release-id <id>`；写新目录，不覆盖原数据或既有 release；生成清单、快照和运行视图，输出 release 摘要 |
| `python -m scripts.faq verify` | `--faq-root <release-root> --release-sha256 <digest>`；校验完整发布、题型计数、引用、记录与拆分；无模型调用，不写原包 |
| `python -m scripts.faq build` | `--faq-root <release-root> --release-sha256 <digest>`；重用现有摄入器，核对嵌入配置和 FAQ 构建范围，生成独立可读 collection |
| `python -m scripts.benchmark.run` | 显式 `--faq-root <release-root> --release-sha256 <digest> --split dev\|test`；复用现有真实运行链路，首版只支持 `multi-agent`；dev 支持 `--per-type` 抽样，正式 test 只接受全量 `--per-type 0`，不传 FAQ 参数时保持原 CLI 和计分 |
| `flowpay` | `--faq-root <runtime-root> --release-sha256 <digest>` 显式启动；不传仍为原模式。FAQ 使用独立本地端口和会话目录；已有聊天页通过本地代理接入，不提供模式切换控件 |

## 3. 工具与引用

- 付款／退款查询仅使用会话主体绑定的范围，再叠加用户已给或前轮已核实的筛选条件；退款通过关联付款承接同一范围。参数不包含持有人键、原始 SQL 或任意数据源，缺绑定不执行。禁止旧商户工具、越权源与内部身份进入 FAQ 场景。对无权限与不存在记录统一空结果，不能以错误详情区分；忽略对话中自称的身份。
- FAQ 引用使用当前回答可解析的公开文档引用；记录引用须在句内或紧邻处将记录编号绑定到结论。记录编号须能锚定同会话主体下真实可用的记录快照与所需字段；拒绝仅在用户题面、调用参数、模型草稿或任意历史结果中出现的编号。允许可追溯且未失效的前轮取证。
- 用现有事件查证本轮／跨轮依据。需要补充可观测证据时，不改现有事件类型和数据形状；不得把越界结果或金标塞入 trace。转述式引用与记录号断言统一由分项验证，不把工具命中量当回答得分。

## 4. 评分与报告

1. 从最终用户可见回答和交互状态提取证据引用与行为；评分器语义匹配逐项回传支持判定的回答原文及引用位置，不允许以题面或金标补写原文。文档必须回溯到适用 `doc_id`／小节，记录必须回溯到成功取证的本人记录及其实际字段。引用与字段、版本、当前身份在评分侧独立复核。每个来源分别支持对应断言，不能用「任意一个引用」替代。
2. 澄清题允许正确的追问终态，不要求生成不存在的业务结论；多轮题只有在预算内且完成最终答案才通过，不能重问已补齐的必要条件。多跳题用工具和证据轨迹验证依赖顺序与输入传递，只有两个正确结果但没有依赖不算通过。历史适用不能使用运行当天时钟决定。
3. `pass` 要求所有必需的结论、绑定及行为满足且没出现禁止断言；其余已评结果为 `fail`（包括已知因预算或澄清失败而未完成任务的正常运行终态）。依赖或 Agent 执行故障为 `execution_error`，判分器故障或不可用结果为 `scoring_error`，均不能进入通过分子。报告以 60 道冻结 test 为分母，另列实际执行、已评分、失败、异常数；中断时明确标出未执行。因基础设施或评分故障而未评定的题须在相同冻结条件下补跑，保留异常记录，不能把未完成报告当作交付。
4. 报告至少记录 release 及双摘要、collection、split、模型／计分配置（无凭据）、阶段与每题状态；给整体、各题型、各难度及失败项统计。发布物的正确性与系统能力分开，不设最低通过率。先在 dev 与固定夹具校验判分，才解封正式 test；不得根据 test 结果再调参。
