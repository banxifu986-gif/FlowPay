# 实施决策：FlowPay 大众版 FAQ

## R1 — 并行发布，不混库

**决策**：沿用现有发布清单和入库工具，FAQ 独立 release、collection 和只读业务快照。用冻结 release 清单的固定摘要校验整包身份；用现有 canonical 业务清单的 SHA-256 加 release ID 配对业务快照与知识集合。完整发布验收核对全部组，本地后端只挂载运行所需组。正式评测按 split 挂载对应题单和金标。

**理由**：现有资源快照已核对 collection 和业务策略的 release ID/hash（`backend/src/flowpay/core/execution/resources.py:162`）。不混搜原知识库，避免内部口径和错误版本被带入。

**未选**：合并后用 `audience` 过滤；它只是一层可见性标记，不能表达数据集与快照的配对。也不把评测标注随 demo 后端挂载。

## R2 — 新快照复用范围机制，不复用原商户记录

**决策**：新造模拟付款人、付款与退款，使用现有登录契约。FAQ 模式使用专用账号文件，只准受限的模拟身份；每个付款人映射到独立的受认证账户范围，内部／无绑定主体在此模式不放行。沿用现有 `merchant` 角色作为传输标签，不代表业务受众是商户。评测按题面绑定同样受限的主体，不以内部身份运行。关闭 FAQ 模式的跨会话记忆。

**理由**：`SessionManager` 已从认证主体强制注入范围并按用户名核对会话归属（`backend/src/flowpay/core/execution/manager.py:136`、`:526`）；现有查询按商户＋环境，不等同于本人归属。保留既有 UI 角色形状可避免新增生产角色或界面。

**未选**：用用户提供的记录号或 `customer_id` 充当所有权认证、让模型选择所有者、以内部身份代跑；复制旧样本仍需重做退款与归属，不提升首版评测价值。

## R3 — 复用阶段，让真实能力暴露在基准中

**决策**：FAQ 首版只跑现有 `multi-agent` 阶段，通过装配选择付款人场景的最小工具和提示，不复制整个 Agent。只补新资料接入、付款／退款核验及必要的 FAQ 行为。不以评测成绩为由改原工作流策略；010 在线断言门不作为 FAQ 评分器或交付前置。

**理由**：现有 bench 逐题独立会话（`scripts/benchmark/run.py:373`），已有渐进披露驱动（同文件 `:159`，`scripts/benchmark/simulated.py:42`）。现有 `make demo` 仅跑确定性协议后端，不合需求；现有 Web 聊天页以登录、会话和 SSE 契约运行并支持更换代理目标（`frontend/src/lib/session-api.ts:33`、`frontend/vite.config.ts:8`）。

**未选**：新做聊天页面、复制一条独立 Agent 链路或用固定答案演示。改口、主动追问和其他阶段延期。

## R4 — 判已发布的断言及绑定，而不是检索命中率

**决策**：FAQ 评分独立于原 300 题评分；先用可测试的结构、引用与事件规则判定证据和行为，再用现有模型客户端语义匹配已发布回答的必需、禁止断言。语义匹配结果必须给原文跨度和具体引用；结构、出处和字段一致性由评测器复核。评分失败明确记为未评定，不回退词面匹配，也不算通过。

**理由**：现有 `evidence_pass` 以文档命中为主，记录只按工具返回 ID 统计（`scripts/benchmark/evidence.py:82`）。工具结果中看到记录、最终提到记录号与用该记录证明一句话是三件事。

**未选**：凭通篇相似度给分；把原 010 审计草稿事件作金标；把金标、预期查询、用例名称交给助手。结构与语义两层均应覆盖反例。

## R5 — 时间、难度和拆分可复跑

**决策**：FAQ 保留可引用的现行与历史口径，正文写明适用时间，前置元数据用于验证版本关系。固定题面可用的判定日期或可查的交易发生日期，不使用执行当天的隐藏时钟。dev/test 按型精确分配，难度整体按 30/50/20 分配且各型都有各档；变体和共享记录按组分割。题目与金标同版冻结，但独立于助手输入。

**理由**：同一 FAQ 是两边合法共享的知识，不是题面变体。按词面改写拆分会高估表现，按文档隔离则把任务变成知识不可达。

**未选**：按难度绑定题型；隐藏历史版；自动把检索排序第一的版本当作正确口径。
